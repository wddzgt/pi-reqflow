# 需求承接边界

本项目的工程目标是解放初级研发：多 Agent 负责需求澄清、方案分析和针对性的质量检查，Pi 负责代码调查、实现和修复。自动完成的对象是已有系统中目标明确、方案可收敛、能独立验证和恢复的需求。业务规则、计算、状态流转、前后端联动、报表和局部缺陷修复均可进入分析，类型不限于 CRUD。

高复杂度长任务不自动完成。需要反复作架构取舍、分阶段设计、协调外部团队或探索未确定方案时，应说明源码依据、尚需作出的设计决策及交接原因，由研发人员借助其他工具逐步设计。设计收敛后，可重新提交独立、明确的子需求；Agent 不得自行拆单来绕过复杂度边界。

耗时长、文件较多、需要多轮编码或测试修复，不单独构成高复杂度。`designStages` 表示需要分别决策的设计阶段，不是编码步骤或修复轮数。普通源码事实应由 Agent 继续查证，不能把读代码的工作交还给用户。模型判断不能证明零风险，实际检查与变更审核仍需保留。

## 方案阶段的四种结论

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| 可承接 | 方案可收敛，影响、验证和恢复依据明确 | 指定研发成员审核方案后实施 |
| 条件承接 | 已知会改变历史行为、接口、数据或产生可逆外部影响 | 一次 QA 检查，跨前后端依赖再追加对应专项；具名负责人审核影响与恢复依据 |
| 待补充 | 有未知影响、阻断问题、缺少验证或恢复依据 | 补充必要事实，重新分析；不得改代码 |
| 超出承接边界 | 需多阶段设计或外部协调、存在高复杂度排除项或不可逆操作 | 交给负责人借助其他工具主导设计；不自动拆单绕过 |

复杂度和影响分别记录，不用综合分数抵消红线。前后端同一功能可以归为一个交付单元；业务模块须说明依据并覆盖每个拟改文件。多阶段迁移、架构重建、核心安全重做、框架升级、探索性研发、不可逆数据操作均不自动承接。项目配置的 `restrictedPaths` 禁止自动修改。不能仅凭目录名 `migrations` 判定为复杂迁移；编写已明确的迁移文件不等于获得执行生产数据操作的授权。

文件数、模块数、验收项数和估算改动量是规划参考，超出时记录审核提示，不单独拒绝需求。时间、工具调用、快照大小、受限路径及高复杂度工作边界仍强制执行。参考值不是经过统计证明的成功率阈值。

| 配置项 | 默认 | 口径 |
| --- | ---: | --- |
| maxFiles | 12 | 拟改及实际修改文件数量，包含测试 |
| maxAcceptance | 8 | 最终需求的验收条件数量 |
| maxBusinessModules | 2 | 需要修改的业务模块数量 |
| maxDeliveryUnits | 1 | 可独立交付的部署单元数量 |
| maxEstimatedChangedLines | 1000 | 方案估算差异行数，仅为辅助判断 |
| maxChangedBytes | 250000 | 实际变更文件的总体积，各文件取修改前后较大值，非 diff 字节数 |
| maxPlanAttempts | 3 | 累计方案分析参考值；仅 strict 执行硬限制，adaptive 允许具名研发继续收敛 |
| maxModelCalls | 36 | adaptive 为累计响应参考目标；strict 为累计响应硬限额 |
| maxTotalTokens | 200000 | adaptive 时为项目用量目标；strict 时为累计 token 硬限额 |
| budgetMode | adaptive | 按复杂度估算并记录超出目标；strict 启用硬 token 门禁 |
| restrictedPaths | [] | 额外需人工主导的项目相对目录或文件 |

## 执行门禁

分析之前，在隔离副本执行现有检查并记录基线。已有测试失败作为诊断证据交给 Pi；属于本需求的缺陷可以继续修复，无关故障必须明确说明。检查无法执行或修改源码时停止；交付前配置的检查仍必须全部通过。只有最终定版需求传给研发，原始沟通留在审计中。方案逐条列出新行为断言和历史回归断言，必要时覆盖边界与失败路径。超界或信息不全时不继续调用专项 Agent；可承接方案按影响选择专项检查，避免每个小需求固定多轮调用。专项检查阻断真实矛盾、风险和缺失决策，不因实现尚未编写或方案措辞不够详细反复验收。

方案及承接证据绑定需求、源码基线、配置、规范与专项检查哈希。指定研发成员批准后才实施；单纯修改配置不能沿用旧批准。默认 `implementationScope=project`，允许 Pi 为同一验收目标在项目授权路径内补充必要文件，新增范围及体积提示进入实际变更记录。`implementationScope=plan`、快速路径、负责人收窄的方案和具名局部修复仍按精确文件清单限制写入。项目外路径和受限路径始终拒绝。验证后由负责人审核实际差异，才能部署测试环境，再由人工验收。条件承接需求不进入快速路径。

主流程只接受研发对具体技术方案的确认，不能用一次笼统授权代替方案确认。`approve-plan` 确认后连续实施、验证，再由研发选择本地验证或发布固定测试环境；`develop` 在未确认方案时停在待确认状态。需要新业务决策或复杂设计的需求明确转人工，不通过反复改写方案绕过承接边界。实际变更、测试和部署均记录证据，不增加强制的逐次变更审核。普通前后端分工本身不构成复杂跨团队协调。

数据和外部动作须提供独立恢复依据，文件快照只能恢复文件。模型可以漏判业务影响；机器验证范围和哈希，研发负责核实分析是否准确。工具守卫不是进程沙箱，仍需使用方配置受控的检查和部署环境。

编码阶段使用现有检查设施，正式验证独立执行。自动恢复按具体失败诊断判断：同一检查问题连续三次未改善时保存现场暂停，不因总修复次数停止有进展的工作。环境、权限、检查自身错误及源码被检查修改仍停止。格式纠错保留完整 schema 校验，问题变化时继续，同一校验问题连续三次重复时停止；不能省略风险或验收项。

默认 adaptive 根据文件数、模块数和估算变更行数提供 3万/6万/12万 token 阶段目标；方案分析目标6万。请求需要更多额度时审计记录目标扩展，实际用量完整累计，超过 token 或累计响应目标不直接终止需求。strict 才按剩余累计 token 与响应次数拦截。只读阶段的请求与工具次数同样是目标，实际模型上下文容量和权限仍是硬边界；所有阶段都限制单次模型请求时间，不设阶段或需求累计时间上限。用量未知时 strict 停止，adaptive 保留未知标记后允许继续；自动修复检查连续失败是否收敛，方案修订硬限制仅适用于 strict，adaptive 允许责任人显式继续收敛。初始化单独计量，失败与重试不重置用量。

### 负责人诊断后续执行

模型误读源码或恢复性质时，负责人可对当前 `plan_review` 提交明确反馈重新分析，也可按已归档 AI 建议更新待审核方案。默认 adaptive 不把第三次修订当成高复杂度或停止人工收敛的理由；仅 strict 保留明确次数限制。实际用量、累计时间和费用不重置，旧结论完整保留，全部承接门禁照常检查；不能通过修订反馈将超界方案改成可批准，也不能自动开始实施。

已接单且批准原方案的研发负责人可以执行 `resume-implementation --evidence-file <诊断文本> --files-file <JSON文件清单>`，随后单独执行 `implement`。仅支持测试部署之前、本地隔离工作区内的同范围代码修复。数据功能必须在原批准方案中具有独立恢复依据，外部影响只能为无或可逆；不可逆、未知、缺少恢复依据仍拒绝。可以续执行零变更或已检查的部分修改；必须明确诊断和文件范围，源码、工作区、快照、策略、规范及原方案仍一致。此操作不执行或恢复运行时用户数据，测试与部署环境由使用方隔离。

续执行前单独归档原状态、差异和文件快照，并记录具名诊断事件；后续修改不会覆盖这份历史证据。管理员及需求负责人可通过核心证据接口查询已保留的尝试，报告和快照篡改会报错。局部修复复用核验源码、完整冻结需求和批准方案；即使完整提供待修改文件，仍保留依赖、调用方和测试夹具的读取与搜索能力。只有内部明确指定不再调研的精确修复才关闭研究，并要求已核验的源码依据。成功工具结果中的重复差异从后续模型上下文压缩，原始日志完整保留，失败消息和累计用量不删减。

已审核的精确替换可追加 `--reviewed-edits-file`，无模型调用，故不要求尚有模型余额；不恢复额度，仍执行全部权限、源码、策略和快照检查。执行后只是待验证，仍需完整回归、差异审批和验收，不计为自动首次通过。

模型持续不遵循方案时，原责任人可追加 `--model-selection-file`，内容为 `{provider,model,thinking}`，必须与项目已配置的模型或旧配置中的已批准候选完全一致。此显式选择记录在续执行事件和实际遥测中，不改配置或审批范围，不重置用量，不能与精确替换同时使用。额度耗尽或调用失败均停止，系统不自动切换模型。

不重新创建工作区、不重置用量，也不豁免审批、回归、差异审核与测试验收。越界修改、用量缺失、基线漂移、严格预算耗尽、数据/外部影响恢复不明确时禁止续执行。单次阶段调用门禁到达后仍需责任人明确诊断才可继续。只有已授权研发流程内有明确诊断的可恢复错误才自动继续，也不把续执行成功计为首次通过。

## 使用方配置

### 处理专项评审误报与澄清

专项 Agent 可能误读源码。已接单研发成员可以用 `resolve-plan-findings --resolution-file <JSON>` 逐项处理当前方案的全部 blocking findings，然后单独执行 `approve-plan`；产品、其他研发和管理员不能代替责任人。此操作不调用模型、不重置预算、不修改原方案或原专项意见。

JSON 包含 `implementationGuidance` 和 `items`。每项包含 `findingId`（`角色:该 finding JSON 的 SHA256`）、`disposition`（`false_positive` 或 `clarified`）、`reason` 和 `sources`（`file/startLine/endLine`，每段最多 80 行）。服务端读取实际源码归档原文与整文件哈希，核对当前策略、基线与检查证据。必须逐项对应，不能遗漏、重复或以空理由消除阻断。处理意见绑定方案版本与分析哈希，篡改或新方案版本会使其失效。网页可回看原意见、责任人的理由和证据，提交入口目前提供核心 API/CLI。

只有原始承接分析本身满足边界时可以使用；未知影响、开放问题、超限、多阶段设计等不允许通过此操作覆盖。它记录人的判断，不证明风险不存在。源码事实与待实施的验证澄清仍需负责人核实，之后照常审核实际差异、运行回归并验收。修改设计范围时必须重新分析方案。

未提供 `admission` 时启用完整内置策略。提供时必须给出全部字段，未知字段、缺失字段和非法路径直接报错。没有关闭承接或审批红线的开关。以下 JSON 可保存为 `admission.json` 后修改项目限额。

```json
{
  "maxFiles": 12, "maxAcceptance": 8, "maxBusinessModules": 2,
  "maxDeliveryUnits": 1, "maxEstimatedChangedLines": 1000,
  "maxChangedBytes": 250000, "maxPlanAttempts": 3, "maxModelCalls": 36,
  "maxTotalTokens": 200000,
  "budgetMode": "adaptive",
  "restrictedPaths": ["src/auth", "database/schema.sql"]
}
```

```sh
node src/cli.js policy-show --project /path/to/project
node src/cli.js admission-draft --project /path/to/project --config /path/to/current.json --policy-file /path/to/admission.json --output /path/to/candidate.json
node src/cli.js policy-preview --project /path/to/project --config /path/to/candidate.json
```

候选文件不会覆盖现行配置或已有候选。预览确认后由项目维护者应用到项目 `.reqflow/config.json` 并运行 `baseline-refresh`；受影响的待审批方案必须重新分析、重新批准，已批准任务会因配置绑定失效停止，应由负责人处理并重新建需求。网页是可选适配器：默认展示结论、范围和责任人，限额与依据按需展开。核心 CLI 与 API 使用同一门禁。

## 衡量首次通过

管理员项目报表提供首次实施及验证通过率，实施失败、变更检查失败、中断或首次验证失败均计为未通过；已经实施但尚未验证的需求不进入样本。每个需求只取第一次结果，避免忽略实施失败或靠重试抬高数字。

报表另列首次配置检查通过率，编码会话内首次检查失败也计为未通过，随后修复成功不抹除失败。独立正式验证继续取第一次结果。分页和筛选不改变项目总体指标，无样本显示暂无样本。这两项不等同于人工验收通过率或线上无缺陷率。质量优化应依据失败原因、回归遗漏和人工验收结果，不能靠减少检查提高数字。
