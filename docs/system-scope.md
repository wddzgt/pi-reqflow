# 系统目标与实施范围

本文记录本轮确认的目标与后续实施取舍，不代表所有能力已经完成。历史设计文档与本文不一致时，以本文为后续修改依据。

## 目标与正常流程

面向公司已有系统，自动完成业务明确、改法清楚、影响可验证的初级研发需求。Pi 承担源码调研、修改与实施中必要的修复；外围流程负责保持需求一致、明确人工责任、安全执行和保存交付证据。

管理员导入项目并建立项目理解 → 产品与 AI 澄清业务并确认需求终版 → AI 提出技术方案和验收对应的测试方法 → 研发沟通、修改并确认具体方案 → Pi 开发，测试 Agent 核对覆盖并运行真实检查 → 研发选择本地验证或发布固定测试环境 → 人工验证并归档。

正常流程中的人工决定是业务需求确认、技术方案确认和最终业务验证。重复审批实际差异、人工逐项授权工具、手工点击测试部署，不作为每个简单需求的固定环节。真实失败和风险必须明确显示，并保留当前证据及下一步处理方法。

角色保持管理员、产品、研发。权限属于账号；只有管理员导入项目，不为每个项目另建管理员身份。产品界面讨论用户、场景、业务规则、范围与验收；研发界面讨论改法、影响、测试和恢复。

## 必要能力

| 能力 | 为目标解决的问题 | 最小实现边界 |
| --- | --- | --- |
| 项目初始化 | AI 能理解老系统并定位功能 | 源码证据、业务入口、运行与测试方法、待核实事项；相关内容按需读取 |
| 业务沟通 | 避免需求理解偏移 | 保存对话，形成版本化业务需求；产品确认后冻结 |
| 承接判断 | 避免自动承接复杂长任务 | 判断业务是否确定、源码证据是否足够、实施路径与影响能否核实、测试能否证明完成 |
| 方案沟通 | 研发知道如何实现并可纠正 | 支持对话与直接编辑候选方案；AI 核对需求偏移、可行性、影响与测试，给出依据和建议 |
| 开发与测试 | 完成真实代码改动 | Pi 隔离执行；按验收检查正向、边界和相关回归；有界修复实现错误 |
| 测试环境 | 人能访问并验证结果 | 使用项目真实部署方式，记录实际版本、状态与访问地址；不能用占位命令冒充发布 |
| 审计与恢复 | 谁提、谁确认、怎样实现可查 | 保存版本、身份、差异、检查与部署证据；保留隔离副本、快照和冲突检查回滚 |
| 有界上下文 | 减少幻觉、重复调用与费用 | 阶段相关上下文、按需历史检索、会话压缩、累计计量 |

高复杂度、重大接口或数据变更、影响未知、需要多轮架构设计或持续人工纠偏的任务，转人工主导。不能通过拆成很多小任务绕过这一边界。研发修改方案不能覆盖未知事实或自动改变冻结业务需求；业务变化应回到产品确认。

导入和了解项目不应以完整执行配置为前提。先发现现有运行、检查及部署入口；执行前必须具备真实可用的配置。自动发现不能将文件或脚本的存在直接认定为运行成功。

## 记忆与检索

短期记忆是本需求当前阶段的对话、候选方案、未决问题和近期反馈。长期记忆是已确认的项目事实、最终需求、批准方案和已验收的交付证据。模型猜测、未确认建议、失败尝试不升级为长期事实；失败记录仍保留在审计中。

原始对话和工具日志完整留存，但不等于每次全部发送给模型。归档记录不能自动推定功能已经进入当前源码，尤其是只部署测试副本的交付。

只有需要核对既有功能、历史业务规则、兼容性、重复需求或相关模块影响时，才发起历史检索。限定当前项目和明确问题，先取少量摘要与证据引用，再读取必要原文；没有相关命中应明确报告。禁止默认注入最近 N 条归档。

上下文压缩保留冻结需求、当前批准方案、未决问题、风险、执行状态和证据引用，压缩已解决的讨论和重复工具结果。摘要不能替代批准文件或改变权限。

## 开源复用与扩展

| 选择 | 本轮取舍 | 依据 |
| --- | --- | --- |
| Pi | 继续作为唯一代码执行引擎；优先复用会话、工具扩展、事件和原生压缩 | [SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[压缩](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md) |
| 历史检索 | 使用 MiniSearch，配合中文分词与项目过滤，摘要检索后按验收项读取原文 | [MiniSearch](https://github.com/lucaong/minisearch)；索引可由完整归档重建，无 embedding 调用与额外服务 |
| 命令录入 | 使用 shell-quote 解析管理员输入，拒绝管道、重定向和隐式环境展开 | [shell-quote](https://github.com/ljharb/shell-quote)；实际执行仍使用参数数组，不增加任意 shell 工具 |
| Chroma | 当语义检索确实改善漏检时采用官方客户端；当前不是导入或交付的依赖 | [官方文档](https://docs.trychroma.com/)、[JS 查询与过滤](https://docs.trychroma.com/reference/js-collection) |
| LangGraph | 本轮不叠加第二套流程状态；需要跨进程恢复等能力时再评估是否替换现有控制器 | [持久化与恢复](https://docs.langchain.com/oss/javascript/langgraph/durable-execution) |
| 检查与部署 | 复用项目已有测试框架、检查器和部署工具；适配真实命令或既有流水线 | 不另写通用测试框架或自建发布平台 |

多 Agent 按业务理解、技术方案、代码实施与测试职责工作，传递同一版本的需求及必要证据。简单需求不按每种技术栈再创建一轮专家评审；只有明确影响需要时才增加专项。测试职责必须覆盖验收，不能把新增测试文件作为完成条件。

扩展位置限于实际可能替换的模型、检索和部署接入。检索索引应可从归档重建，不能成为审批或审计的唯一依据；后续换检索后端不应改变业务流程。暂不建设通用插件体系、记忆中台、知识图谱或动态 Agent 调度平台。

## 继续实施的顺序与完成标准

1. 收敛导入和角色交互；导入不要求用户理解内部配置结构，缺少运行配置时清楚显示待配置事项。
2. 补齐研发方案对话、直接编辑、客观分析与具体版本确认；业务变化明确返回产品确认。
3. 补齐按需历史检索与短期对话整理；优先复用 Pi 压缩并核对现有预算、证据和审计记录。
4. 验证确认方案之后连续开发、测试，在验证方式选择处停下，研发可先本地验证，再显式发布测试环境、人工验收及归档；不加固定重复审批。
5. 用少量有代表性的真实简单需求验证完成率、错误承接、人工纠偏次数、可访问测试环境和实际模型成本。

本轮已实现导入与运行配置分离、研发方案对话和编辑提案、具体版本确认、按需历史检索、短期讨论整理，以及 Pi 原生压缩的批准事实保护和累计计量。固定测试环境可暂不配置，方案设计仍可进行；开始自动开发前必须准备真实检查。检查通过后，由负责研发选择本地人工验证或发布配置的测试环境。HTTP 地址可访问性明确记录，最终业务验证由人完成。源码、原始沟通、版本和失败证据仍保留。

自动测试覆盖本地流程、权限、过期审批和记忆检索；真实 Pi 与模型测试需显式启用。测试结果不代表所有业务系统的完成率，实际项目仍需验证模型、回归命令和发布入口。

完成标准是用户能顺畅交付符合承接边界的真实简单需求，拒绝或转人工的原因客观清楚，交付版本和责任可以查、变更可以恢复。材料齐全和单个模型回答成功，都不能单独证明交付完成。
