# 研发设计与分工审核

产品阶段仅确认业务目标、范围和验收结果。研发方案从已冻结需求和真实源码生成，描述如何实现以及测试怎样证明完成。旧版方案仍可读取；完整设计需要重新生成新版，系统不会静默改写历史方案。

方案可审核时，负责研发点击“确认方案并开发”，在同一窗口准备本次自动检查。已有项目检查命令直接带入，也可从真实 package.json 脚本或 Maven 测试配置选择、填写命令。构建和静态检查明确标注，不视为业务测试通过。命令随当前需求的人工批准记录保存，开发、验证、合并检查使用同一份命令；不修改管理员管理的 Git 和固定发布环境配置。缺少固定测试环境仍可开发，完成后由研发选择本地人工验证或合并发布。

## 连续执行与失败恢复

研发接单时可直接准备方案，方案仍需人工确认。确认后在同一操作内完成隔离开发和自动检查，检查成功后停在验证方式选择，由研发选择本地验证或发布测试环境。发布到异步流水线后自动查询本次执行结果。

开发保存 Pi 原生会话，后续继续复用已读取的上下文和现有代码。每个会话检查点保留独立文件与哈希，恢复前核对方案、代码快照、授权目录和 Git 分支版本。旧任务没有会话时保留代码现场，明确重新读取必要源码。

一次开发操作最多自动恢复一次：测试命令执行失败时继续诊断修复；工具次数或执行时间到限且有会话或修改现场时尝试续跑。恢复仍使用需求累计预算，不重置配额、不扩大批准范围、不自动合并发布。权限或范围违规不会自动恢复。仍失败时显示暂停原因和“从现场继续开发”入口，不要求重新填写业务需求或再次批准同一方案；现场发生变化则拒绝旧页面的继续请求。

## 方案展示

- 实现思路，说明复用哪些现有能力、如何保持旧行为。
- 普通需求默认不出图，包括前后端同时修改的需求；调用顺序、状态与错误处理由文字和接口约定说明。只有能明显帮助理解时，才补一张短流程图或时序图。
- 前端和后端各自的设计说明，不涉及的部分不填。
- 接口约定，包括复用、修改或新增，请求、响应示例和错误行为；已有接口要引用实际源码文件。
- 数据处理和恢复方式。
- 拟改文件、类或方法位置、修改说明和关键逻辑伪代码，也可使用少量关键代码片段。聚焦核心判断、身份映射与写入边界，通常 5–10 行；不输出完整类、组件或全部实现。同一逻辑只在核心文件展示，纯展示、配置或样式文件无关键逻辑时可留空。
- 对应业务验收的检查、相关回归、具体风险与待确认事项。

正文以简短思路、前后端改法、验证和风险为主，图示、接口样例、文件细节与伪代码按需展开。普通技术选择由 AI 给出推荐和源码依据，只有影响业务结果、数据处理范围、授权或调查后仍未知的风险才向人提问。已确认的决定不反复追问。

图示是辅助说明，不以缺少图示阻断方案；选择出图时仍检查语法声明和禁止执行指令。历史方案中的图示继续展示，不会因新规则被改写。方案的业务验收、源码依据、接口一致性与研发分工确认仍需完整保留。

每个待确认问题下方可以直接回复，集中提交一次核对。AI 回复展示推荐做法及理由；没有必须人工决定的事项时，可直接点击“按 AI 建议更新方案”，生成待审核版本，无须复制建议或重新填写修改意见。研发仍需确认实际方案后才能开发。直接编辑也仍是提案，AI 应客观核对源码与冻结需求，不能因为研发身份认定其合理。

“没有待回答问题”与“方案检查已通过”分别展示。沟通仅形成建议，不改写当前方案或解除技术阻断；即使 AI 建议保留方案，仍有技术问题时也提供“核对沟通结论并更新方案”，核实意见并修正设计，无须填写额外回复。数据库新增、更新和逻辑删除均需具体且可验证的恢复步骤；代码回滚不会恢复数据。可复用真实已有的备份恢复方式，不强制新增独立脚本或范围外的用户撤销功能。

生成方案时，明确技术矛盾先在 AI 内部处理：冻结需求不变，专项检查反馈给设计 Agent，最多一次局部修正，再核对修正后的方案。没有阻断就直接交给研发审核，不需要人转述前后端或测试意见。已有待定业务决定、业务变化提案或复杂任务不会触发内部代答。调查后仍未知的影响继续阻断，不能凭修正文案放行。

内部修正仅返回必要字段和设计小节，未修改项显式为 null，由控制器保留原值；不能修改需求哈希。完整草稿落盘，通过带精确草稿哈希的 read_plan 按需读取相关小节，不在每次纠错请求中重复整份方案。修正记录、失败用量、检查依据均保留；复核中断后复用相同输入和哈希的修正，不再次生成。更换需求、源码、规范或本轮意见会使复用失效。

测试设计修正按冻结验收编号逐项更新：verification 为 null 表示全部保留，否则为包含所有验收编号的对象，每项为 null（保留）或 {scenario, regression}。修改说明和关键伪代码按 file 更新，接口按 method/path 更新或新增，未返回条目显式保留；这些修改数组不能删除条目。控制器保留原顺序和未改内容，不把局部结果替换成完整列表；新增文件和接口仍需通过完整范围与源码校验。其他数组（例如 affectedFiles）仍是完整替换。纠错输出接入已有生成校验，格式和合并后的内容不合法时在同一次 Pi 调用内最多修正两次，使用同一冻结需求及精确草稿，计入原有时间和模型预算；仍失败就明确报错，不提交无效方案。

仍未解决的技术问题清楚展示，但不逐项生成答题框；真正的业务待确认问题保留各自回复框。内部修正不自动批准或开始开发。旧版方案或内部修正后仍需调整时，保留“让 AI 按检查意见修正方案”和编辑、沟通入口。人工请求再次更新属于新一次明确操作，不是后台无限重试。更新时以已有接口索引和按需读取的设计为基础，保留合理决定；修改恢复方式不能顺带重建接口和类结构。

方案更新失败后，原方案、沟通和修改提案继续保留。页面展示失败记录和“按已保存意见重试更新”，无须再填写内容。仍可继续沟通，或调整提案再更新；新增修改意见分别留档，重试读取最新提案并结合后续沟通。重试成功仅形成待审核方案；更新未完成时不能批准旧方案进入开发。重试仍执行既有的权限、版本、完整性与预算检查。

## 两种协作方式

产品在方案设计前选择协作方式并指派已注册的研发账号。全栈模式一人接单并审核完整方案。分工模式指定不同的前端和后端研发，由其中一人兼任交付负责人；一次接单同时接受此人的相关职责。

分工成员都能查看需求、讨论和修改同一份方案。只确认方案实际涉及的前端或后端部分，双方都负责核对共同接口与交互。确认不会立即执行代码。交付负责人在必要确认完成后选择需求分支并启动开发，开发测试通过后选择本地验证或合并发布。

审核记录保存账号、时间、方案版本与审核内容哈希。修改后重新比较实际内容：仅改变后端局部设计不会自动清空前端确认；需求、源码基线、配置、公共接口、共同设计或验收内容变化会使相关确认失效。旧审核记录仍可追溯。过期页面确认明确报错。

## 接入方式

`assign-team` 的 `team` 可以是 `{mode:"single",lead:"dev1"}`，或 `{mode:"split",frontend:"dev1",backend:"dev2",lead:"dev2"}`。账号角色仍为 `developer`。接单动作沿用 `accept-assignment`，指定 `developer`、`frontend` 或 `backend` 职责。

`review-plan` 传 `{part:"frontend"|"backend",expectedPlanHash}`。`getRequirementEvidence().planReview` 返回当前有效的分工确认状态。最终 `approve-plan` 仍由交付负责人操作；其他成员不能借分工职责提交代码或发布。

CLI 对应 `assign-team --team-file <JSON>` 和 `review-plan --part frontend --plan-hash <hash>`，认证沿用既有入口。

## 仓库边界

人员分工与代码目录结构分开判断。同一仓库的前后端可以由一人或两人负责；普通独立目录也可联合导入，在隔离副本中开发并本地验证。同一 Git 仓库只使用一个需求分支和受验代码版本。

当前不支持把两个独立 Git 仓库拼成一个项目后自动联合提交发布。它们应分别导入；跨仓库统一方案和双版本发布需要后续明确实现，不能将目录复制或人员双审核冒充跨仓库交付。

无论分工方式如何，需要多阶段架构设计、影响不可核实或无法可靠验证的复杂需求仍由人工主导。普通前后端职责分工本身不构成复杂协调的拒绝理由。
