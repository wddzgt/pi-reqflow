# 架构与边界

> 2026-10-09：本文件包含历史流程。当前目标、人工确认边界、记忆和开源取舍见 [系统目标与实施范围](system-scope.md)，后续实现以该范围为准。

## 定位

面向已有代码仓库中的小型、边界清楚的迭代需求。核心负责成员分配、流程状态、审批证据、工作区隔离、验证与归档；Pi 只承担只读调研和批准后的代码修改。跨模块设计、数据迁移、重大接口变更与不明确的业务规则，应由人主导方案，流程仍可保存其审查和验证证据。网页工作台是可选适配器，使用方可接入自己的上游系统。

产品录入、多模态资料、研发反馈、需求契约和多角色一致性门禁的完整设计见 [需求对齐与多角色评审](requirement-review.md)。当前已实现网页录入、结构化契约、独立 Pi 角色评审与门禁；附件理解仍待实现。

## 角色与阶段

| 阶段 | 执行者 | 必要证据 |
| --- | --- | --- |
| 项目全局初始化 | 本地项目维护者、确定性扫描器 | 源码与配置指纹、前后端及数据/中间件声明线索、文件路径、未知项、历史基线哈希链 |
| 提交需求 | 需求方 | 原始需求文档 |
| 分配与接单 | 产品负责人、被指定成员 | 角色、成员、接单结果与事件哈希 |
| 研发反馈与产品确认 | 研发审核人、产品负责人 | 问题答复、版本化契约与哈希 |
| 角色理解评审 | 独立 Pi 角色或对应人工角色 | 同一契约哈希、只读评审文件、验收覆盖与差异检查 |
| 方案生成 | Pi | 一页内的需求与验收、拟改位置、验证、回退和必要的待确认问题 |
| 方案审核 | 人 | 审核人、方案哈希、项目基线与配置哈希 |
| 实施 | Pi | 隔离工作区、变更清单、修改前文件快照、原始事件 |
| 验证 | 流程执行器 | 配置的检查命令及日志、变更边界检查 |
| 实际变更审核 | 已接单研发审核人 | 全部修改文件、验证版本哈希、简短结论与具名风险责任人 |
| 测试发布与验收 | 发布适配器、人 | 部署记录、人工验收记录 |
| 合并候选验证 | 流程执行器 | 实际候选版本的检查日志 |
| 发布和观察 | 发布适配器、人 | 发布审批、部署记录、观察记录 |

生产发布可以由配置明确禁用，此时测试验收并验证候选版本后归档。CLI 和网页动作从项目级访问令牌取得身份，再按需求归属、成员分配、接单状态和角色授权；`admin` 只读全项目审计，不可代行交付审批。本地令牌仍不等于组织级 OIDC/SSO 身份。

快速路径由项目显式配置并由已接单的执行人启动。产品确认仍是业务输入门禁，无未答问题、现有文件和无影响依据明确时，流程生成方案并暂停，不强制启动 QA 与研发角色双重评审，也不强制修改测试文件。已接单研发审核人批准方案后，Pi 才能在隔离工作区实施；自动验证后再次暂停，由同一审核人核对实际变更并留下简短结论。审批绑定契约、方案、基线和验证后文件哈希，以及全部变更文件；测试部署会复核这些证据。任何现有文件都可能影响历史功能、接口或数据，Agent 的接口判断不构成放行。范围检查失败时尝试回退隔离工作区。快速路径最多推进到测试环境，测试验收仍由人完成；Git 模式的提交与推送仍由人负责。

## 存储与回退

每个目标项目用 `.reqflow/` 保存配置、索引和按需求 ID 分隔的归档。事件逐条追加并形成哈希链；每次状态改变附带操作者、时间与证据路径。链能发现局部篡改，但同机管理员仍可重写整条链，正式审计需要外部不可变存储或签名锚点。

新建需求时原始需求正文的哈希也写入首个事件；后续读取需求时核对归档原文。

`init` 自动生成项目全局基线。扫描只依据当前文件清单、依赖清单和项目配置，不运行模型或服务；输出 `baseline.json`、`baseline.md` 及按内容哈希保存的历史版本。基线事件形成单独哈希链。角色评审和方案生成必须使用与当前源码、配置一致的基线，并在需求事件中保存基线哈希；源码变化后维护者需显式刷新。无法从静态证据确认的运行关系和数据约束保持“待核实”，不能把依赖声明当作实际生产拓扑。

实施前保存允许处理文件的完整基线，实施后保存变更清单和文件副本。回退只作用于隔离工作区，并在写入前检查文件是否又被人修改；发生冲突直接报错。Git 模式另用需求分支与 worktree，分支命名、基线分支和发布分支由项目配置。系统不自行提交、推送、合并或删分支。

回退前还核对审计中的变更清单、基线清单与整个备份内容的哈希和文件模式，任一证据改变时拒绝恢复。Git 基线、已发布需求提交和合并候选提交都检查已跟踪文件；含 `.env` 或配置排除路径时拒绝继续，因为 Git worktree 会直接检出这些文件，路径拦截不能替代这一检查。

同一需求的执行人与方案/变更审批人、测试验收人和发布审批人必须不同；分配阶段检查职责冲突。访问令牌必须唯一，创建和加载身份文件均拒绝重复令牌。不同需求的事件写入与索引更新由项目锁串行执行，最多等候十秒；Pi 和检查执行不持有项目锁。Jenkins 提交和轮询请求有时间限制，轮询共享总时限，认证请求禁止自动跟随重定向。

规划前先在隔离副本运行配置的检查，以确认已有功能的测试基线。检查命令、退出状态、日志路径和 SHA-256 摘要一起进入事件；方案审批、实际变更审批、测试部署和发布门禁会复核相应日志。Pi 实施中途失败时检查已写入文件，保存变更清单后可回退。候选版本验证后保存内容哈希，发布和归档前必须与该哈希一致。

每次 Pi 调用把 trace ID、阶段、模型、耗时、提示词字节数与哈希、各类 token、费用、工具次数和日志路径写入需求事件；失败后也保留可取得的用量。单需求观测通过核心 API 和 CLI 输出，管理员报告汇总当前页。未产生 Pi 调用的预算跳过事件单列，历史缺失指标不填零。方案提示词使用已冻结契约作为唯一业务依据，不重复发送原始需求全文。

## 安全与成本边界

Pi 在规划阶段仅能调用读取工具，在实施阶段才开放编辑工具；路径策略由扩展拦截。工作区排除 `.env` 文件，测试命令通过明确的 argv 配置执行。配置版本 2 要求分别为 Pi、检查、本地部署声明环境变量名称白名单；系统令牌和 Jenkins 凭据不会由父进程环境自动传给子进程。单次 Pi 调用有时间、工具次数和事件日志大小上限。自定义模型没有价格元数据时，金额上限无法可靠执行，必须先为正式部署补齐模型定价和计量验证。

代码规范另有内置通用约束和八种常见语言的精简预设；按需求契约文件后缀选择，并与项目全局规则一起进入角色评审、方案和实施。规范摘要哈希绑定评审与后续门禁；内置规则不会自行安装或运行对应语言的扫描器。需要硬性检查时，使用方将已固定版本的工具接入 `checks`，并由具名审核人处理不能自动判断的规则。

项目检查可选 Docker 沙箱：固定镜像摘要、只挂载需求工作区、禁网、只读根文件系统、独立临时目录、移除 Linux capabilities，并限制内存和进程数。规划前基线、实施后和候选版本检查均沿用同一配置；日志与审计记录镜像摘要。Docker 需由部署方预装并可信运行，镜像需预先准备。Pi 与本地部署命令仍在宿主机运行。

Pi 扩展与进程组清理都不是操作系统沙箱；能自行创建新会话的代码仍可脱离当前进程组。当前只提供本机项目级令牌身份和角色映射；跨机器团队环境还需为 Pi 配置容器或等效隔离、组织级身份认证、TLS 入口、凭证隔离、外部不可变审计、仓库信任策略、Jenkins 实例集成测试和生产回退适配。

可选 Docker/Compose 部署将 CLI、Web、Pi 和本地检查放入一个受限制的服务容器，参见 [Docker 部署](docker.md)。默认仅发布本机端口、显式限定 Web origin、保留身份与审批校验，目标仓库/审计、工作区和 Pi 状态分别持久化。该部署未提供每任务独立容器或出站网络控制；不挂载 Docker socket，不支持直接嵌套现有 Docker 检查沙箱。宿主机 CLI 启动方式继续保留。
