# 架构与边界

模型职责固定为需求、开发、审查三个 Agent。目标、人工确认边界及承接范围见 [系统目标与实施范围](system-scope.md)，上下文与原生编码机制见 [上下文设计](context-engineering.md)。

## 定位

面向已有代码仓库中的小型、边界清楚的迭代需求。核心负责成员分配、流程状态、审批证据、工作区隔离、验证与归档；Pi 只承担只读调研和批准后的代码修改。跨模块设计、数据迁移、重大接口变更与不明确的业务规则，应由人主导方案，流程仍可保存其审查和验证证据。网页工作台是可选适配器，使用方可接入自己的上游系统。

产品录入、图片资料、研发反馈、需求契约和风险审查见 [需求对齐与方案审查](requirement-review.md)。当前已实现网页录入、图片多模态输入、结构化契约和综合审查；通用文档提取仍待补齐。

## 角色与阶段

| 阶段 | 执行者 | 必要证据 |
| --- | --- | --- |
| 项目全局初始化 | 本地项目维护者、确定性扫描器 | 源码与配置指纹、前后端及数据/中间件声明线索、文件路径、未知项、历史基线哈希链 |
| 提交需求 | 需求方 | 原始需求文档 |
| 分配与接单 | 产品负责人、被指定成员 | 角色、成员、接单结果与事件哈希 |
| 研发反馈与产品确认 | 研发审核人、产品负责人 | 问题答复、版本化契约与哈希 |
| 需求对齐 | 需求 Agent、产品负责人 | 当前行为、业务目标、范围与版本化验收 |
| 方案生成 | 开发 Agent | 文件与实现设计、接口和数据影响、验收用例、检查范围及本地启动方式 |
| 综合风险审查 | 审查 Agent，按风险调用 | 同一契约与方案哈希、前后端和测试风险、源码依据及具体发现 |
| 方案审核 | 人 | 审核人、方案哈希、项目基线与配置哈希 |
| 实施 | Pi | 隔离工作区、变更清单、修改前文件快照、原始事件 |
| 验证 | 流程执行器 | 方案选定的相关检查及日志、跳过依据、变更边界检查；无自动检查时等待人工验证 |
| 实际变更审核 | 已接单研发审核人 | 全部修改文件、验证版本哈希、简短结论与具名风险责任人 |
| 测试发布与验收 | 发布适配器、人 | 部署记录、人工验收记录 |
| 合并候选验证 | 流程执行器 | 实际候选版本的检查日志 |
| 发布和观察 | 发布适配器、人 | 发布审批、部署记录、观察记录 |

工作台在研发检查通过后支持人工确认交付直接归档，本地验证和测试环境发布作为可选路径，不提供正式环境配置入口。人工确认、实际本地验证、测试环境验收分别记录为 manual、local、deployed，归档前复核代码版本与检查证据；未执行的环境验证不计为通过。CLI 使用项目令牌，网页使用登录会话；服务端按需求归属、研发分配、接单状态与角色授权。管理员管理项目、账号、模型并查看全项目审计，不能跳过责任分配和审批门禁。当前身份机制不等于组织级 OIDC/SSO。

项目环境入口独立于需求详情。`configure-environment` 允许管理员和已接受当前项目分工的研发操作，不授予模型管理或其他需求审批权限。测试发布沿用配置哈希和基线绑定；本地配置记录在单独哈希链 `local-environment-events.jsonl`，不改写已有方案与审核证据。只读扫描生成应用、依赖、变量、证据与启动影响；默认完整应用，可选择仅前端或单个服务。明确必需的依赖不能关闭，未知项需要具名选择。保存校验扫描哈希和配置修订；重新扫描必须确认差异后应用。

私有值存入权限为0600的独立版本文件，审计保存引用和摘要；页面仅返回普通字段和密码是否已配置。项目外 dotenv 文件只作显式导入来源，之后不持续读取。启动按批准命令对应服务，每个进程仅注入该服务的配置；完整应用缺少对应命令时明确报错。Spring 数据源地址覆盖保留已扫描的非凭据 JDBC 参数。profile、外部配置等未覆盖组合明确阻止相应服务验证，不作运行成功承诺。扫描不执行源码或连接依赖；检查只探测受支持依赖的 TCP 端口，启动前重新检查，数据库写入影响须确认环境修订。失败返回 `blocked` 并追加需求事件，需求仍保留在已验证代码阶段。

本地验收核对启动时的配置修订；停止服务后修改环境配置，必须重新启动并验证。配置保存、启动与验收共用配置锁，防止检查后配置被并发替换。独立环境检查另有 `local-environment-check-events.jsonl` 哈希链，保留检查人、配置修订、时间和逐项结果。

快速路径由项目显式配置并由已接单的执行人启动。产品确认仍是业务输入门禁，无未答问题、现有文件和无影响依据明确时，流程生成方案并暂停，不强制启动 QA 与研发角色双重评审，也不强制修改测试文件。已接单研发审核人批准方案后，Pi 才能在隔离工作区实施；自动验证后再次暂停，由同一审核人核对实际变更并留下简短结论。审批绑定契约、方案、基线和验证后文件哈希，以及全部变更文件；测试部署会复核这些证据。任何现有文件都可能影响历史功能、接口或数据，Agent 的接口判断不构成放行。范围检查失败时尝试回退隔离工作区。快速路径最多推进到测试环境，测试验收仍由人完成；Git 模式的提交与推送仍由人负责。

## 存储与回退

每个目标项目用 `.reqflow/` 保存配置、索引和按需求 ID 分隔的归档。事件逐条追加并形成哈希链；每次状态改变附带操作者、时间与证据路径。链能发现局部篡改，但同机管理员仍可重写整条链，正式审计需要外部不可变存储或签名锚点。

新建需求时原始需求正文的哈希也写入首个事件；后续读取需求时核对归档原文。

`init` 自动生成项目全局基线。扫描只依据当前文件清单、依赖清单和项目配置，不运行模型或服务；输出 `baseline.json`、`baseline.md` 及按内容哈希保存的历史版本。基线事件形成单独哈希链。角色评审和方案生成必须使用与当前源码、配置一致的基线，并在需求事件中保存基线哈希；源码变化后维护者需显式刷新。无法从静态证据确认的运行关系和数据约束保持“待核实”，不能把依赖声明当作实际生产拓扑。

实施前保存允许处理文件的完整基线，实施后保存变更清单和文件副本。回退只作用于隔离工作区，并在写入前检查文件是否又被人修改；发生冲突直接报错。Git 模式另用需求分支与 worktree，分支命名、基线分支和发布分支由项目配置。Git 提交、推送和测试分支合并须由负责研发查看变更后明确授权，Pi 编码不会自行执行这些操作；系统不删除需求分支。

回退前还核对审计中的变更清单、基线清单与整个备份内容的哈希和文件模式，任一证据改变时拒绝恢复。Git 基线、已发布需求提交和合并候选提交都检查已跟踪文件；含 `.env` 或配置排除路径时拒绝继续，因为 Git worktree 会直接检出这些文件，路径拦截不能替代这一检查。

人工角色为产品、研发、管理员，前后端分工属于研发职责。研发接单并确认自己负责的方案部分，交付负责人批准实施并核对实际变更，人工验收单独留痕。访问令牌必须唯一，创建和加载身份文件均拒绝重复令牌。不同需求的事件写入与索引更新由项目锁串行执行，最多等候十秒；Pi 和检查执行不持有项目锁。Jenkins 提交和轮询请求有时间限制，轮询共享总时限，认证请求禁止自动跟随重定向。

方案根据源码、验收和依赖选择检查范围，说明未选检查的理由，并在隔离副本执行所选基线检查。检查命令、退出状态、日志路径和 SHA-256 摘要一起进入事件；方案审批、实际变更审批、测试部署和发布门禁复核相应证据。无合适自动检查时明确等待人工验证。Pi 中途失败保存已写入文件和实际差异，之后可继续或回退。候选版本验证后保存内容哈希，发布和归档前必须与该哈希一致。

每次 Pi 调用记录 trace ID、阶段、模型、耗时、提示词字节数与哈希、token、费用、工具次数和日志位置；失败后保留可取得的用量。审计事件流省略流式碎片和思考全文，私有 Pi 会话另行保存。单需求观测通过核心 API 和 CLI 输出，管理员报告统计全项目，明细分页。未产生模型调用的跳过事件单列，缺失计量不填零。方案以冻结契约为业务依据，编码以批准交接与当前源码为依据。

执行控制独立于耗时动作：暂停会中止模型、工具、检查和启动进程，记录现场，刷新后仍可发现运行状态；继续前校验当前版本与责任人。代码回退后可在同一需求“返回研发方案”，重新出方案和批准，使用新的隔离工作区，旧快照与历史消耗继续保留。

## 安全与成本边界

Pi 在规划阶段仅能调用读取工具，在实施阶段才开放编辑工具；路径策略由扩展拦截。工作区排除 `.env` 文件，测试命令通过明确的 argv 配置执行。配置版本 2 要求分别为 Pi、检查、本地部署声明环境变量名称白名单；系统令牌和 Jenkins 凭据不会由父进程环境自动传给子进程。单次 Pi 调用有时间、工具次数和事件日志大小上限。自定义模型没有价格元数据时，金额上限无法可靠执行，必须先为正式部署补齐模型定价和计量验证。

代码规范另有内置通用约束和八种常见语言的精简预设；按需求契约文件后缀选择，并与项目全局规则一起进入角色评审、方案和实施。规范摘要哈希绑定评审与后续门禁；内置规则不会自行安装或运行对应语言的扫描器。需要硬性检查时，使用方将已固定版本的工具接入 `checks`，并由具名审核人处理不能自动判断的规则。

项目检查可选 Docker 沙箱：固定镜像摘要、只挂载需求工作区、禁网、只读根文件系统、独立临时目录、移除 Linux capabilities，并限制内存和进程数。规划前基线、实施后和候选版本检查均沿用同一配置；日志与审计记录镜像摘要。Docker 需由部署方预装并可信运行，镜像需预先准备。Pi 与本地部署命令仍在宿主机运行。

Pi 扩展与进程组清理都不是操作系统沙箱；能自行创建新会话的代码仍可脱离当前进程组。当前只提供本机项目级令牌身份和角色映射；跨机器团队环境还需为 Pi 配置容器或等效隔离、组织级身份认证、TLS 入口、凭证隔离、外部不可变审计、仓库信任策略、Jenkins 实例集成测试和生产回退适配。

可选 Docker/Compose 部署将 CLI、Web、Pi 和本地检查放入一个受限制的服务容器，参见 [Docker 部署](docker.md)。默认仅发布本机端口、显式限定 Web origin、保留身份与审批校验，目标仓库/审计、工作区和 Pi 状态分别持久化。该部署未提供每任务独立容器或出站网络控制；不挂载 Docker socket，不支持直接嵌套现有 Docker 检查沙箱。宿主机 CLI 启动方式继续保留。
