# Git 与研发交付

pi-reqflow 在研发确认方案后使用独立需求分支开发。正常流程为：确认方案和分支 → Pi 开发及相关测试 → 研发审阅实际变更 → 人工确认交付 → 归档。本地验证与测试发布均为可选；选择测试发布时，研发须另外确认提交、推送及发布版本。

侧栏「环境配置」由管理员及已接受当前项目分工的研发维护，本地配置与测试发布配置分别保存。系统扫描项目并按服务生成配置表单，默认完整应用，也可选择仅前端或单个服务；启动命令及健康地址来自已批准方案，不接受手填。需要测试发布时，再配置 Git 交付规则及 Jenkins、GitLab CI/CD、GitHub Actions 或已有脚本连接的固定环境。保存或检查配置不启动项目，也不代表验证通过。

## 项目导入

目录属于一个 Git 仓库时，导入完整仓库到工作台隔离副本，保留提交历史、已有本地分支和原远程仓库。不会在原目录开发，也不会把 Git 项目重新拼成 frontend/backend 目录。同仓库的前后端子目录可以一起导入；不同仓库需分别导入。

源目录必须有明确的当前分支、已提交的代码和远程仓库。原目录未提交的修改不会被偷偷丢弃或混入初始化。通常使用 origin；有高级 Git 配置时使用明确指定的 remote；多个远程仓库且无法明确选择时返回配置错误。

Git 项目执行命令沿用仓库相对路径。自动识别已有 package.json 中的 test、deploy:test 脚本；未发现完整执行配置时仍可导入并沟通需求，之后由管理员连接真实测试流水线。

Git 凭证使用服务主机已有的 SSH/凭证管理配置，非交互执行。CI 访问令牌与 Git 推送权限是两回事；配置 Jenkins/GitLab/GitHub 的 CI 令牌不会自动授予 Git 推送权限。HTTP Git URL 不允许嵌入密码、令牌或查询参数。

## 分支与确认

研发确认方案时可新建需求分支或选已有独立分支。不能直接用项目基础分支、正式目标分支或配置的共享测试分支开发。新分支从方案的固定基础提交创建；其他人之后推进基础分支不会使已经审核的需求自动失效。

已有分支需对应方案基础版本且没有被其他工作目录占用。分支代码不一致时必须针对其代码核对方案，系统不会把不适用的方案直接搬过去。第一版没有自动重新规划不同基础版本的已有分支。

Pi 只修改工作目录并运行检查。方案确认不会自动授权 Git 提交。开发测试通过后停止在研发确认点；发布按钮展示具体变更、分支、测试结果和目标环境，点击确认才授权本次提交、推送及配置的合并。

提交身份为 pi-reqflow；具名研发审核记录、需求哈希、方案哈希及实际代码哈希保存在审计中。系统不强推，不改写共享历史，不覆盖已有暂存区。其他人员推进了需求分支时需研发核对，不能当作 Agent 已审核代码。

## 本地验证

“启动本地验证”在需求工作目录运行已确认方案的启动命令，等待各服务的 `healthUrl` 返回成功后展示 `applicationUrl` 应用入口与启动日志，无需填写命令或地址。无应用页面的服务入口明确为 `null`，只展示健康检查状态与日志；选择单个服务只展示该服务的入口。可停止服务；启动失败明确报错并停止本轮进程，保留日志和代码。重新检查本地修改或回退前停止服务，改动后须重新启动与验证。

CLI/库没有常驻服务时明确显示不适用，按方案中的验收场景验证。项目没有合适自动测试时，代码就绪状态明确标注人工验证待完成，不能当作功能测试通过。相关检查通过后可直接人工确认归档，不要求配置或启动环境，也可选择发布已配置测试环境再验收。需求、方案、代码哈希及具名审批仍有效。

Git 项目同时提供需求工作目录、基础版本和下载补丁。补丁包含新增及删除文件，使用独立临时索引生成，不修改开发工作目录的暂存区，也不提交代码。

在另一台电脑，用相同基础提交的独立工作目录应用补丁：先 git apply --check，再 git apply。希望把本地修改回传时，补丁应是相对于本次 Agent 结果的增量。可先暂存 Agent 补丁到本地索引，在本地修改后使用 git diff --binary 导出增量；本地无需合并或提交。

通过“重新检查本地修改”检查服务目录修改或上传增量补丁。原变更证据和快照保留，当前变更重新归档并运行测试，旧代码审核和推送版本失效。补丁应用前检查路径和范围；不符合范围的修改不能进入发布。

本地验证声明是人工记录，不伪装成自动测试证据。返回服务器后继续使用同一个发布按钮，不另设强制本地验收。

## 两种测试发布方式

管理员或已接受当前项目分工的研发在「环境配置」的测试发布页配置一次，后续需求复用。

- 直接部署需求分支（默认）：确认后提交、推送需求分支，再部署其固定提交。测试发布不要求合入团队主分支。
- 合并到指定分支后部署：配置 gitDelivery.testMode=merge 和 testBranch。确认按钮明确显示目标分支；系统拉取最新目标版本，在独立候选目录合并，运行项目检查，确认目标未在检查期间推进，再提交、正常推送并部署已检查的合并提交。

例如配置：`"gitDelivery": { "testMode": "merge", "testBranch": "integration" }`。复用公司的既有测试分支，不自动创建公司分支策略。

目标分支更新、推送被拒绝或合并冲突都返回明确错误并留痕。冲突目录保留，研发可在其中解决、暂存；重新打开发布操作会显示候选差异，确认其哈希后重新验证并继续。失败的推送重试不会再次生成相同需求代码提交；进程在提交和留痕之间中断时需人工核对实际提交。

测试流水线必须支持指定分支/版本，并核对实际 checkout SHA。Jenkins/GitLab/GitHub 接入和 URL 可访问性不会证明部署应用就是指定代码。测试合并版本的检查、部署参数和轮询均绑定同一个候选版本。

仓库分支保护规则由远程仓库执行。第一版使用普通 Git 推送，不创建 PR/MR，也不绕过审核要求；要求 PR/MR 合入的公司应在托管平台完成合并，再走现有版本核验流程。后续可在相同交付接口接入托管平台的合并 API。

共享测试环境同一时间只允许一个部署处于运行或结果待核实状态；其他请求得到明确等待提示。不会为了发布排队把所有需求的开发串行化。同一验证地址被其他需求用于发布后，旧需求会提示并阻止直接验收；负责研发可以确认重新发布已验证版本，原部署日志保留。

禁用生产发布的项目，人工验收后归档的是测试交付。记录需求分支、已推送版本、测试候选版本和责任人；归档不代表已经合入正式主干。启用生产发布的项目继续保留独立的候选验证、批准和观察流程。
