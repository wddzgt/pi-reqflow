# 项目代码规范约束设计

当前已内置通用规则与 Java、JavaScript、TypeScript、Python、Go、Rust、C#、Kotlin 八种语言的精简预设，并支持项目级全局规则。规范会进入相关角色评审、方案和实施提示词，版本哈希进入审计与后续门禁。系统不会自动安装或执行 P3C、ESLint 等工具；只有项目配置的检查命令和人工审核能提供验证证据。

## 目标与默认规则

规范约束针对代码和设计质量，独立于需求审批、身份、隔离和发布门禁。通用默认规则应覆盖所有语言：先定位根因和完整数据流；只改需求必要范围；遵循仓库已有分层、命名和错误处理方式；新增行为提供可执行测试；禁止吞异常、伪造成功、静默默认值、无依据的空值过滤与“为不报错而加的特判”；不要顺手重构或增加无需求依据的抽象。

“禁止防御式编程”不能机械地解释为禁止一切校验。外部请求、文件、数据库和第三方响应在信任边界必须校验；非法输入应明确报错。禁止的是已经有契约保证的内部数据被反复猜测性兜底，以及用 fallback 掩盖上游错误。Agent 发现输入异常时，先定位产生错误的上游；无法确认根因就停止实施并提出问题。

当前自定义规则支持 `review` 与 `guide`。`review` 进入审核上下文，具名研发审核人负责判断；`guide` 指导写法。主观规范不能仅靠模型自评升级为机器 `block`。需要强制阻断的格式化、静态扫描、编译和测试规则，应接入项目 `checks`；检查失败时现有流程会阻断。

## 项目和语言规范

当前按需求契约的文件后缀选取适用语言预设。内置预设只给出有来源的精简写法要求，并要求遵循仓库现有配置，不会修改 `.editorconfig`、构建文件或静态扫描配置。项目全局规则附加到所有需求，不能关闭内置通用规则或语言预设。更细的组织、模块和目录级覆盖仍待实现。

Java 文件自动匹配内置的“阿里巴巴 Java 开发手册黄山版”精简预设。阿里官方仓库提供手册和 P3C PMD、IDE 实现；自动扫描只覆盖其可机器检查的一部分，异常处理、设计和数据库规则仍需其他检查或人工审核。使用方可通过预览看到该预设；若团队要严格执行 P3C，需把已固定版本的检查器命令加入项目 `checks` 并先验证存量代码基线。

使用方可声明团队特有的全局规则，例如禁止在 Controller 直接访问数据库、DTO 字段命名或数据库迁移要求。每条规则需要稳定的 `TEAM-*` ID、简短文本和 `review`/`guide` 等级；最多 30 条、每条最多 400 字。自由文本可以指导 Agent，但不能伪装成已自动验证的强制规则。

## 项目全局规则配置

在项目配置 JSON 中添加 `codingStandards`；内置规则始终生效，无需复制整本手册。示例：

```json
{
  "codingStandards": {
    "globalRules": [
      {
        "id": "TEAM-ERR-001",
        "text": "不得捕获异常后仅记录日志并继续返回成功；追踪异常源头并明确失败",
        "level": "review"
      }
    ]
  }
}
```

团队需要机器检查时，在受控项目配置的 `checks` 中声明实际命令及对应运行环境。规范文本本身不能包含可执行脚本。当前检查结果记录命令、退出码、日志哈希；工具和规则集版本应由团队在检查命令或仓库锁文件中固定。

## 交互与执行顺序

维护者可用 `standards-draft` 对配置执行 `add`、`replace` 或 `remove`，生成新的候选 JSON 文件；它拒绝覆盖已有输出文件，也不会改写正在使用的项目配置。再用 `policy-preview` 查看内置目录、团队规则和与已安装配置的差异；`standards-preview --files` 只显示指定文件适用的规则和规范哈希。初始化后可用 `standards-show --files` 查看现行规则。预览明确标记 `verification: not-run`，不会声称规范已通过检查。候选配置由维护者按现有受控文件流程应用；网页配置编辑器尚未实现。

```sh
node src/cli.js standards-draft --project /path/to/project --config /path/to/current.json --action add --rule-id TEAM-ERR-001 --text "异常必须传递或明确返回错误" --level review --output /path/to/candidate.json
node src/cli.js policy-preview --project /path/to/project --config /path/to/candidate.json
node src/cli.js standards-preview --project /path/to/project --config /path/to/candidate.json --files backend/src/Service.java,web/src/view.tsx
node src/cli.js standards-show --project /path/to/project --files backend/src/Service.java
```

需求评审、方案和实施只加载与契约文件相关的精简规则摘要，不反复发送整本规范。角色评审、方案和实际变更审批记录规范哈希；版本变化会拒绝继续。实施后运行已配置的确定性检查，再由具名研发审核人处理无法机器判定的规则。当前尚未自动生成逐条规则的违反位置和豁免工作流，审核人需要结合代码差异和检查日志判断。

老仓库往往已有历史违规。首次接入机器检查前应先在原始代码上运行，避免存量问题让每个小需求都无法启动。按新增违规阻断、存量债务清单和具名豁免的自动化机制尚未实现，不应声称系统已能自动区分新旧违规。

规范版本或团队规则变化后，既有方案的规范哈希失效。后续报告应持续区分“机器检查通过”“人工审核通过”“未配置检查器”和“存量违规”，避免把提示词遵循误报成质量保证。
