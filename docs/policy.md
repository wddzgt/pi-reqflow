# 默认约束与项目配置

本文件描述流程门禁和运行配置。代码质量、语言预设及使用方团队规则另见 [项目代码规范约束](coding-standards.md)；`policy-preview` 展示规范配置，但不执行代码扫描。

需求、开发、审查三个 Agent 可分别配置模型，见 [Agent 模型配置](agent-models.md)。`policy-preview` 显示每个 Agent 的最终 provider/model 和配置来源；模型修改纳入项目配置哈希。

## 规则分层

系统默认门禁来自核心状态机，项目配置不能关闭：产品确认版本化契约；具名研发审核与该契约绑定的方案后才能改代码；实施后跑通方案选定的相关检查，由具名研发审核人确认真实变更和检查结果，再人工确认交付即可归档。本地环境配置、启动验证和测试环境发布均为可选；选择环境验收时必须核实对应代码和环境版本。无合适自动检查时保留待人工验证标记并记录实际人工检查结论，不伪称测试通过。生产发布另需发布角色审批；所有状态与证据进入需求审计。Pi 不自行提交、推送、合并或删除 Git 分支。实施前保留文件快照，回退遇到后续修改会拒绝覆盖。

代码回退后，需求等待研发决定，可以点击“返回研发方案”在同一需求内重新开始。已确认需求和研发分工保留，旧方案与快照归入历史，新一轮根据当前源码生成下一版方案，重新确认后才开发；使用新的独立工作区，Git 默认创建带重启次数的新需求分支。旧审批、检查结论和部署记录不能批准新一轮代码，历史用量与预算计量继续累计。返回方案本身不调用模型、不启动开发，也不会回退已发布环境或外部数据。

普通需求采用“必要业务澄清 → 冻结目标、范围与验收 → 方案及开发授权 → Pi 实施与真实检查 → 人工验收”的路径。角色理解评审可选，前后端同时改动不会自动触发三个模型评审。默认 `planReview` 为 `risk-based`：持久化数据影响或外部效果需要独立综合审查恢复与验证依据；普通接口和历史功能改动由方案责任人及真实验收、回归检查把关。未知风险、未解业务问题和不可逆操作仍受承接门禁约束。配置 `planReview: "full"` 对每份方案执行一次综合审查。只接受三个 Agent 配置键，旧版本活动方案需要重新分析，不修改历史证据或伪造审批。

项目显式配置执行器、模型、可改路径、环境变量白名单、资源上限和发布方式。检查配置是可选候选，研发方案读取仓库脚本、测试与调用依赖后确定本次范围，研发只确认方案，不填写执行命令。密钥、发布环境和分支不能猜测。`fastPath` 未配置时关闭；模板显式关闭生产发布。运行检查的 Docker 沙箱是可选配置，未设置时会在策略预览中明确提示宿主机执行边界。

隔离源码目录不能直接使用原项目的可写依赖。对源码快照中含 `package.json`、且本机已安装 `node_modules` 的目录，规划检查和实施准备会复制独立的依赖副本；恢复开发只补齐缺失的依赖目录。内部相对链接保留，绝对链接及指向依赖目录外的链接明确拒绝。依赖不进入模型源码、变更快照和交付差异，复制路径进入工作区准备审计；系统不自动安装包或执行安装脚本。Docker 内需要使用与容器系统及架构匹配的依赖。

| 由项目配置 | 建议的初始选择 | 配置时需核对 |
| --- | --- | --- |
| 可改路径与排除路径 | 只列实际源码与测试目录；排除环境文件、构建产物 | 能否触及接口、数据库迁移、生产配置及敏感文件 |
| 验证约定 | 方案包含验收场景、相关检查与跳过理由、本地服务启动命令和真实地址 | 按源码依赖选择测试范围，包括改动的共享调用方；无关失败不阻塞、不修复。没有自动检查时记录人工验证待完成，构建不代表功能验收 |
| 检查运行环境 | 可信仓库可用受控主机；不可信检查配置固定摘要的 Docker 镜像 | 镜像、依赖、文件权限、网络与 Docker 守护进程 |
| 资源与成本 | 按团队模型价格和项目规模设置上限 | 自定义模型的价格元数据是否准确 |
| 快速路径 | 默认关闭；先在真实历史需求样本上试运行 | 文件与验收项数量、可改路径与受影响文件大小；不强制改测试文件 |
| Git 分支与部署 | 需求独立分支；测试部署先用受控环境；生产发布先关闭 | 远端分支、Jenkins 作业和发布责任人的实际流程 |

## 运行限制怎样对应真实项目

限制分为项目快照、单个需求范围、阶段资源和模型单次请求四层，不能用一个超时覆盖全部工作。下面是内置演示/网页导入的起点及核心默认策略，CLI 模板和已配置项目可能不同；不是经过所有模型验证的最优值。

| 限制 | 当前起点 | 评估与调整依据 |
| --- | --- | --- |
| 源码快照 | 网页导入100 MiB；CLI本地模板20 MB | 限制复制与校验资源，不是把整个仓库送给模型。先排除依赖、构建产物和本地资料，再按实际源码体积配置 |
| 需求规模 | 12文件、8验收、2模块、1000预计差异行、1交付单元 | 这些是承接参考值，超过后需更完整的实施验证安排；结构化方案最多30拟改文件。跨团队协调、多阶段迁移与不可逆操作仍应人工主导 |
| 单次模型响应 | 新部署300000 ms，可按Agent覆盖 | adaptive 按每次请求计时；strict 按阶段计时。结合首响应、正文延迟与完整输出耗时调整，不能用工具耗时推测推理时间 |
| 需求累计时间 | 核心默认20分钟，失败也累计 | 每阶段使用剩余额度并有阶段上限。更大的需求应先看实际分轮耗时和重复调查，时间不足再显式调整 |
| 模型调用与token | 只读最多6请求；累计参考36响应/20万token | 编码采用 Pi 原生执行，不受阶段请求数/token目标拦截。实际用量继续累计；需求时间、费用和模型窗口仍有效 |
| 源码正文与工具结果 | 只读正文6 KB、结果8 KB；编码预装12/24/32 KB | 编码交接当前相关正文，后续工具使用 Pi 原生输出与压缩；完整契约、接口与风险不按摘要截断 |
| 工具与编辑 | 只读阶段有工具次数门禁；替换旧/新各50行 | 编码保留原生源码及命令工具，不强制调查轮次和纠错次数。文件权限、大段覆盖及最终差异审核仍校验 |
| 费用与审计 | 新部署每需求$2、事件2 MB | 自定义模型价格未知时不能认定$0；未计量请求明确停止。审计超限要检查输出与事件类型，不能删除失败证据 |

效率评估同时看成功率、契约/接口/验收保留、实际回归结果、首次与完整响应延迟、每轮上下文字节、输入/输出/缓存token、重读工具次数和检查点复用。源码哈希、方案版本与权限属于硬约束，不应为减少耗时取消。开发 Agent 持续承接设计与实施，审查 Agent 一次覆盖相关领域，避免重复调研和多个角色重写整份方案；时间和token改善需要真实样本对比，不能仅凭提示词缩短宣称收益。

## 配置交互

CLI 是核心入口，网页只需调用同一策略说明函数作为可选适配器。初始化前运行 `policy-preview`，得到内置门禁、项目规则、宿主机执行提示及配置哈希；字段拼写错误、无效范围和不相容的快速路径会直接报错。初始化后 `policy-show` 查看现行规则，再用候选配置运行 `policy-preview` 查看逐项差异。预览不写项目文件，也不代替风险审批。

```sh
node src/cli.js policy-preview --project /path/to/project --config /path/to/candidate.json
node src/cli.js init --project /path/to/project --config /path/to/candidate.json
node src/cli.js policy-show --project /path/to/project
```

自定义页面宜按“项目范围、验证、执行环境、预算、分支与发布”分组填写，先显示当前值与候选值，再显示受影响的门禁和明确的宿主机提示。只允许编辑项目规则，不提供关闭内置门禁的开关。保存前由服务端调用 `validateConfig`，保存后重新生成全局项目基线；已审批需求的配置哈希不一致时，现有门禁会拒绝继续，需在新基线上重新评审。当前项目没有在线修改配置的 API，管理员通过受控文件流程管理配置。

## 当前不能由配置解决的边界

Pi 与本地部署仍在宿主机，路径守卫和环境变量白名单不等于进程沙箱。检查沙箱也只覆盖配置的项目检查命令。跨机器团队部署还需要可信身份源、TLS、外部不可变审计与凭证管理；这些不能通过在 JSON 中填写一个“安全”标志获得。
