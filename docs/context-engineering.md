# 执行上下文与预算控制

## 已落实的工程措施

- 初始化生成 `PROJECT_REFERENCE.md` 和 `agent.md`，旧生成文档经哈希验证后从缓存迁移，不额外调用模型。供人阅读的完整指南保留；日常模型读取结构化概览、架构、规范和待核实事项。
- 项目原有 agent.md、AGENTS.md、AGENTS.override.md、CLAUDE.md 单独读取并核对源码哈希，原文件不覆盖。实施携带根目录及所改文件祖先目录的规则原文，不用模型摘要替代规则。
- 同一需求跨阶段复用已经核实的原始源码，正文总额度6 KB；同一片段不重复加载。跨需求默认提供文件、行号和哈希索引，有明确相关文件范围时才装入事实。专项评审不读取其他 Agent 的结论。
- 专项交接完整保留冻结需求、验收场景与回归、接口输入输出及异常、数据设计、风险和恢复、拟改范围、待确认事项，以及契约/方案/源码/上下文哈希。统一发送受影响的前后端设计正文；组件位置作导航，伪代码和图表用 `read_plan` 按精确草稿哈希及章节取回，每次最多1000字符。纠错后的活动草稿及复用检查点也可读取。省略不是缺失，不能据此阻断；确有依赖必须核对原文。
- 方案草稿和已完成专项检查保存检查点。同一需求、源码、基线、配置、规范及审核反馈未变时，重试仅调用未完成检查；回归基线检查仍完整执行。任何校验不匹配或证据篡改都停止，不把过期结论当作当前审批依据。
- 实施按方案中的真实函数名和引用行号定位当前源码，标明完整文件与局部片段；批准文件中唯一的文件名引用可解析到其完整路径。有相关定位时不预装无关的文件头。小需求预装正文12 KB，标准需求24 KB，有界复杂需求32 KB；这是交接额度，编码中的读取与搜索使用 Pi 原生输出协议。
- 实施交接携带已批准的完整设计，包括前后端处理、接口字段及错误、组件位置和关键逻辑、数据与恢复依据；文件修改摘要不能替代详细设计。该设计同时进入原生压缩后的权威上下文，避免恢复执行时重新猜测接口或渲染方式。
- 具名修复由已接单的方案审批人给出诊断和文件范围。源码、工作区、快照及审批必须仍匹配；提供诊断相关函数与完整冻结契约，Pi 自行核实实施需要的证据。
- 研发方案的 `validation` 与需求、验收场景、文件改法一起传递：只执行影响范围内的 `checks`，记录 `skipped` 的依赖依据，不修复无关失败；`startup` 描述实际本地服务，缺启动脚本的改动须列入方案。无自动检查的 `manualReason` 明确人工验证步骤。压缩后的权威上下文保留这份完整约定，执行与交付不再从项目全量检查或手填命令另取一套规则。
- 编码保留 Pi 原生系统提示、源码工具和 bash 命令工具，允许自行调查、编辑和验证。每次替换最多50行，权限与整文件覆盖规则继续校验；普通工具错误交给 Pi 修正，不通过两次纠正上限结束会话。不再使用特殊完成标记、关闭工具或改写收尾提示。
- 模型文字不代表交付成功。编码中的检查结果绑定其执行时的源码快照，失败如实保留为诊断，不拿旧快照的失败拦截已修复的代码。控制器检查实际差异，对当前候选运行正式检查，通过后研发可人工确认交付并归档；本地验证与测试发布可选，选择环境验收时核对相应环境版本。同一快照的通过证据可以复用，不增加固定重复审批。
- 产品上下文仅保留当前未解决的人类补充、最新分析和未确认候选。已经形成候选的早期讨论改为事件引用；大段原始需求只给有界预览，缺失细节用 `read_discussion` 读取当前需求的精确原文。原文不删除，摘要和候选不是已批准事实。
- 研发沟通保留完整冻结需求，发送方案导航、意见导航和本版本最近四条有效交流摘录，历史摘录合计最多4000字节。项目规范原文、接口样例、伪代码和历史对话留在磁盘；有具体判断需要时，使用 `read_plan` 按精确方案哈希及章节读取，每次最多1000字符，或 `read_discussion` 按事件哈希读取原文。摘要及引用进入审计，失败日志不作为研发意见，压缩后仍保留冻结需求和版本引用。直接编辑是待核实提案，AI 建议不能绕过业务边界和研发确认。
- 复用 Pi 原生压缩，压缩后重新注入冻结需求、批准方案、权限、当前状态和证据引用。编码按模型实际上下文容量减去最大输出额度触发压缩，不插入自定义字节或请求额度门禁。只读结构化阶段继续执行 strict/adaptive 预算及摘要调用预留。原生摘要计入同一需求用量，失败明确停止，未返回计量时明确标记未知用量。
- 归档不默认进入项目上下文。`search_history` 必须给出明确检索理由，仅检索当前项目的已验收归档，最多三条摘要。`read_history` 先匹配本会话搜索结果，再读取一个验收项的有界原文片段，带偏移、总长度和完整证据哈希。历史功能是否存在于当前源码仍需核实。

## 预算口径

需求、开发、审查三个 Agent 各有一个模型选择。方案和讨论复用哈希绑定的私有检查点。正式编码与再次执行启动新的 Pi 会话，只交接冻结需求、批准设计、当前源码、实际变更和失败诊断，不重放历史方案工具或旧编辑成功记录；历史会话仍保留作审计。risk-based 和 full 决定综合审查范围；具名审批、真实测试及回滚冲突检查始终保留。

Pi 恢复原生会话时以会话头的 cwd 创建工具，单独指定子进程目录不会覆盖它。需要恢复的方案会话验证原检查点哈希并绑定当前目录，原检查点不修改；编码直接在实际开发工作区创建新会话。所有阶段启动时核对工具目录与授权目录一致，使源码读写、检查、差异审计和回滚针对同一份文件。

方案和沟通会话中的原生 user 消息由控制器写入。续行时从已验证检查点提取这些阶段指令的内容哈希；本轮完整指令替换模型活动上下文中的旧阶段指令。即使连续两轮正文相同，也只保留最后一份。助手消息、工具参数、源码结果、检查反馈及原始会话不删除，当前冻结需求、方案和权限继续明确提供。`contextReplacements` 记录替换内容的哈希与字节数。编码每次启动新会话，以当前源码及变更交接，不重放旧阶段指令。

初始化、产品沟通、方案、审核和实施共享上下文处理。当前指令已逐字包含的权威对象或长文本不再次注入，只补充缺少的字段，并记录 `reqflow_context_prepared` 的保护哈希、原字节数、补充字节数和内联字段。压缩移除当前指令后重新提供完整权威状态；实施的保护字段还包括规范、检查命令、恢复依据与责任人诊断。不得以摘要代替这些决定。

只读工具的参数和结果均逐字相同时，保留最后一份完整文本，之前的工具结果改为引用其调用 ID 和内容哈希。不同参数、内容变化、错误、检查结果及图片不合并；工具调用和原始记录不修改。`reqflow_read_context_replaced` 保存替换依据。产品阶段尚未定版的业务消息仍保留，不能为了减少字节而丢掉待对齐的业务决定。

需求累计用量覆盖产品分析、方案、专项检查、实施，以及所有失败和重试。`maxModelCalls` 按实际模型响应累计；adaptive 记录目标及超出情况，strict 将剩余调用额度交给执行器。管理员更换模型不重置计数，供应商明确零用量拒绝不占业务响应额度，物理尝试序号仍完整保留。

预算记录覆盖三个 Agent 和所有失败重试。只读结构化阶段继续执行配置的请求数、工具结果和 token 门禁。编码交给 Pi 原生执行，不以阶段 token 估算、请求次数或工具次数提前结束；外层保留单次响应时限、费用和审计大小限制。strict 的累计调用和 token 承接门禁仍在进入阶段前校验，编码阶段自身不再插入新的请求预算控制。

所有阶段中 `maxPiMs` 限制单次供应商完整响应，Pi 启动和一次原生摘要操作也有独立的等待时限。流式增量不延长时限；每次新请求重新计时，完成后停止该次计时，工具等待不挤占下一次请求。需求和阶段没有累计时间预算；历史耗时与未知耗时都不阻断下一轮，耗时和摘要用量仍完整归档。遥测保存单次请求时限、分轮耗时和工具耗时。

一段方案可能需要源码调查、接口核对和结构化输出，应分别观察每轮请求。单次请求超时停止当前执行并保留证据，负责人可在原流程重试，无需追加累计时长。调整计时口径不保证模型本身更快。应同时观察请求上下文字节、首个响应/正文延迟、工具耗时、已计量 token、未计量请求和交接正文大小；方案交接字节不等于整个供应商请求字节，更不等于实际节省 token。

编码请求使用 reqflow_provider_request 被动审计，不限制8/16/24轮，不要求先写代码才能继续调查，也不因压缩预留而拒绝合法请求。telemetry.executionMode=native，requestLimit/tokenLimit=null 表示这些自定义阶段门禁已移除，实际请求、用量和耗时仍完整计量。

只读结构化阶段把序列化上下文字节作为独立目标。adaptive 核对输入预留和输出额度仍在配置窗口内，才允许字节目标扩展并记入 `contextExpansions`。相同模型已返回输入计量时，保存其实际请求消息、工具定义和其他参数的哈希及字节数。相同前缀用 `measured_prefix`；精简或续行后仍保留原内容时用 `measured_retained`，保留全部原输入计量，再为新增或改动的内容预留字节。删除内容不直接扣减已计量 token，重复消息按出现次数匹配。续行计量绑定已验证的原生会话分支及助手响应哈希，不能跨模型复用，错误或中断响应不作为依据。没有有效计量、整份上下文重建或完成原生压缩时，按整份请求预留；压缩后等待新的模型计量。估算无法满足窗口或选择strict仍停止。编码使用原生上下文容量及压缩；工具参数不压缩成占位符。

所有兼容模型阶段都使用独立 Pi 运行目录，按模型窗口和本次输出额度配置原生压缩，不继承机器上个人 Pi 的压缩参数。请求布局正文只存在私有检查点；公开审计及遥测保存布局哈希和消息数，避免每轮复制所有历史指纹到审计正文。

只读结构化阶段在请求前按序列化请求字节数预留输入，strict 不足时停止。当前输入预留为字节数除以二，属于保守估算，**不是供应商 tokenizer 的精确计量**；图片和特殊编码仍有误差。编码不使用此预估门禁。供应商返回的全部输入、输出和缓存 token 为最终计量，失败与重试同样累计。

价格未知时不得把 `costUsd=0` 显示为免费。模型额度耗尽时明确停止，由管理员在模型设置中修改并测试连接；系统不自动切换模型，也不开启付费。

## 失败与审核

新的 Pi 审计流保存最终回答、工具参数与结果、失败、预算及验证事件。增量、消息开始、轮次结束、整段会话结束及重复工具消息不重复落盘；思考正文只记字节数和 SHA-256 指纹，不另调模型生成摘要。原始事件仍用于实时计量、输出校验及流程控制，输入、输出和缓存 token 不因日志精简而扣减。遥测 `auditStorage` 区分收到与保存的字节、省略事件和思考段数；这反映存储变化，不代表模型账单节省。

管理诊断默认展示结果、失败原因、耗时、请求数、工具数及 token；分轮与工具明细按需展开，原始计量和证据元数据再单独展开。历史审计链与证据保留，不清理旧日志。方案、讨论及每次编码执行的私有 Pi 会话仍保留原生格式，用于审计；编码再次执行从当前工作区启动新会话。私有会话与精简的审计流不同，当前不会自动删除。代码快照可回滚代码，不可据此声称数据库或外部副作用已恢复。

文件工具继续校验当前工作区、排除路径、写入权限及替换行数。编码工具的失败和成功结果交给原生 Pi，不整段拒绝合法搜索结果，也不由控制器按两次错误结束会话。bash 在可信服务环境中运行，工作区副本不是主机安全沙箱，命令同样进入审计；最终检查和差异审核不能被模型成功声明代替。只读结构化阶段继续验证输出、证据与资源门禁。

责任人引用源码时，每个范围都写完整文件名，例如 `src/service.py:1-40; src/service.py:100-130`。责任人已归档的方案澄清与批准备注均参与源码定位，写权限由当前项目范围或明确收窄的批准清单决定。

执行器在首个请求发送前明确拒绝的调用记为零用量；已发出但没有完整计量依据的调用仍是未知用量，按下文的 strict/adaptive 规则处理。不能用零值掩盖网络中断造成的不确定结果。

包含中断请求的运行仍保留此前已完成响应的 token、调用次数和累计时间，作为已计量小计；总请求与最终费用标为未知。旧记录即使曾写入 `unmeasuredRequests=0`，只要分轮记录显示请求仍在运行、超时或中断，也不能当作完整计量。strict 模式需要供应商完整计量才能继续；adaptive 模式下 token 是参考值，保留未知标记和已知消耗后允许继续。累计时间及其未知标记仅用于审计，不参与执行门禁。系统不填零、不清空历史用量，也不把未知费用当作免费。


方案只列实际拟改文件，既有回归文件列入验证要求。责任研发人可用 `approve-plan --scope-file` 缩小写入范围并记录理由；不能扩展原方案、解除阻断项或削弱回归。原方案、选择、审批人与证据哈希都保留。

## 参考与取舍

用户暂停通过独立请求触发，不受工作台 busy 状态或任务锁阻塞。执行状态来自服务端当前进程，页面刷新后仍能发现本轮运行；暂停先终止 Pi/命令进程组，必要时强制终止，再完成差异检查、日志关闭和审计保存。不会在用户暂停后自动恢复或自动回退。暂停后的继续操作绑定当前审计头，复用已保存的阶段证据和审批，测试中断只重跑检查，编码从已保留文件进入新会话；不承诺恢复尚未完成的供应商响应。历史消耗和未计量请求均保留。

这些控制针对本机 AI、检查及本地启动流程；Git 推送和外部部署仍遵循原授权、提交及结果核实规则。断开浏览器连接本身不等于暂停，必须通过暂停操作终止后端执行。

- [Aider repository map](https://aider.chat/docs/repomap.html)：采用有界的文件与符号定位信息，相关源码按需读取。本项目尚未实现完整符号依赖图。
- [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：使用轻量引用、按需取证和阶段相关上下文，避免无差别累积。
- [Anthropic multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：职责、任务描述与交接信息需要明确；多 Agent 会增加 token 消耗。本项目以需求、开发、审查三个 Agent 按风险安排调用，减少重复设计，未盲目增加并发模型调用。
- [LangGraph durable execution](https://docs.langchain.com/oss/javascript/langgraph/durable-execution)：参考检查点与可重放任务的设计，保留阶段证据和失败尝试；本项目仍由自己的状态门禁控制部署，不能把不确定的外部副作用当作可直接重试。
